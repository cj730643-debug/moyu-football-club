## 2. 架构

| 层 | 实现 |
| --- | --- |
| 前端 | Next.js 16.3.4、React 19.2.6、TypeScript strict、Tailwind CSS 与自定义响应式样式 |
| 账号 | Supabase Auth；客户端只保存本人会话，并在到期前刷新 |
| 后端 | Supabase Edge Function `mfc-game`，当前 ACTIVE 版本 11，启用 JWT 校验；每次请求另向 Auth 验证真实用户 |
| 数据库 | 隔离的 `mfc` schema；JSONB 房间状态及版本号为事务写入入口，同时维护关系表投影、请求回执和历史 |
| 权限 | 私有表启用 RLS且不向客户端开放；仅服务端可执行 RPC。公开 `mfc_room_signal` 对房间成员只读，非成员无数据 |
| 并发 | 房间行锁与版本比较、请求回执、固定比赛 ID、房间/赛季/轮次唯一约束；建房同请求使用事务锁 |
| 引擎 | MIT 许可的 `tbleckert/football-simulator`，固定提交 `39529b19c40868d66aa47db084ebc9ea29c86e70`；独立七属性/词条适配层。LICENSE / NOTICE 已保留 |
| 比赛存储 | 服务端完整模拟后分批上传录像；完整性检查成功才锁定比分和哈希，失败租约可恢复 |
| Replay | 每秒逻辑帧、60 个比赛秒分块、客户端插值。客户端不计算正式比分；本人看完才公开最终统计，双方看完才结算 |
| 同步 | Supabase Realtime 房间信号，加 12 秒轮询与窗口重新聚焦刷新兜底；实际 WebSocket 重连仍待浏览器验证 |

当前引擎标识为 `football-simulator@39529b1+mfc.3`，模拟适配标识为 `mfc-adapter.5-fair-recovery`。第一季前四轮属于早期适配器 2；从第五轮起冻结私有输入并使用适配器 3。旧录像保留其原版本与哈希，不因代码更新重新生成。保存录像的七场新比赛有私有输入快照，早期四场已有锁定录像但没有该新增快照字段。

## 8. 测试账号流程

1. 下载 `moyu-football.html`，保持联网，在支持现代 JavaScript 的浏览器打开。
2. A 用自己的邮箱和至少八位密码注册；如提示邮箱确认，先确认邮件再回来登录。
3. A 创建俱乐部和好友房间，复制六位房间码。
4. B 在另一个浏览器或无痕窗口，用另一个邮箱创建独立账号，登录后输入 A 的房间码加入并创建俱乐部。
5. 按蛇形顺序各选六人；系统补齐十八人班底。选择培养、阵容、战术，两人分别确认准备。
6. 两人分别播放同一场完整比赛，半场点击继续；断线后返回同一房间继续已保存进度。
7. 双方看完后成长和计分。完成十轮后签青训或交易球员，双方确认开启第二季。
8. 在俱乐部历史打开第一季比赛回看。球员详情可以查看赛季、生涯和本队统计；退役球员的最终评价留在离队/退役档案。两位玩家应分别使用自己的账号。

本报告中的自动测试账号为专用内部测试账号，不向玩家提供其密码。玩家使用自己的邮箱创建第二账号即可开始。
